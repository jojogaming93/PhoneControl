Agent handoff

  • Read hud.md, technical.md and lessons-learned.md before modifying input handling. The distinction between PC logical pointer IDs and Android local pointer IDs is essential.
  • Inspect the actual saved profile before interpreting a key or coordinate. The source starter is WASD; this user's saved layout is ZQSD. Right-click is Tap in the starter but Hold in the saved layout.
  • Keep Android local IDs within 0–9. Rotate available slots for restarted camera swipes; do not change IDs of fingers that stay held.
  • Sprint is an extended joystick gesture. Autorun is a separate HUD tap on =. Do not restore the earlier Shift-to-autorun implementation.
  • Check the handset for Samsung's idle touch-protection overlay before drawing conclusions from a failed input test.
  • Use a separate temporary ADB forward and control server for experiments. Release every finger and remove only the experiment's own resources afterward.
  • A few successful swipes are insufficient. Reproduce repeated camera restarts, a held action, and a new action pressed after sweeping.
  • The user confirmed the final sustained-sweep fix worked. Keep that verified implementation as the baseline.

Mapping a touch interface

Reference layout

PhoneControl translates foreground keyboard and mouse inputs into independent Android touches. The supplied layout is a starting point for a landscape interface, with movement at the lower left, camera dragging in the middle right and editable action buttons. See the root README for the supported-games list.

The positions are normalized coordinates, not universal button locations. Weapon, vehicle, context, aspect ratio and custom HUD settings can change them. Calibrate your own screen through the mapping overlay; keep saved profiles separate from starter defaults.

Movement, aiming and actions

Historical live observations established movement through one held joystick touch, forward sprint by extending that same touch, and autorun through a separate button tap. A separate camera finger could move while fire or scope remained held. Repeated swipes require renewal of the camera finger without releasing other action fingers.

Tap and Hold describe the duration of the PC-generated touch. The application being controlled may apply its own toggle/hold settings. Map contextual actions only when their buttons are visible. Do not infer successful input from healthy mirrored video alone.

Idle overlays and performance

An idle touch-protection overlay can dim the phone, reject touches and reduce delivered video FPS while USB streaming continues. Dismiss it on the handset before assessing mappings. A high stream FPS cap cannot increase the underlying application's render rate.

The stream counter reports delivered frames. Input-to-display latency, eligibility for particular game modes and recognition across other HUDs remain unmeasured. Private screenshots are excluded; the public atlas is schematic and automated image inputs are synthetic.

Coordinate conventions

All coordinates below are normalized fractions of the visible phone image: top-left is (0,0), bottom-right is (1,1). They are not Windows desktop coordinates or fractions of a title bar/window border. This capture was 2340 × 1080 physical landscape pixels. The rendered texture was 1920 × 886 after the maximum-edge setting.

DeviceSession.Touch converts normalized coordinates to physical injection pixels with round(x * (W - 1)) and round(y * (H - 1)). The packet carries the physical W/H, not the texture dimensions. Windows pointer coordinates first have to be converted relative to the actual letterboxed video rectangle.

Use Native.VideoRect when mapping desktop clicks. Preserve the image aspect ratio in a documentation overlay. A 1080 × 2340 natural display becomes 2340 × 1080 in landscape; geometry changes release touches before adopting the new dimensions.

Calibrating another HUD

  1. Obtain a fresh full landscape frame in normal gameplay with the expected weapon equipped. Record W/H and whether it has letterboxing.
  2. Release aiming with Esc. Enter F8 mapping edit mode or use Pick on the Controls page.
  3. Locate each real action, especially contextual interact. Use normalized image coordinates rather than copying desktop pixels.
  4. Check normal joystick motion, forward sprint and return to walking using the same held finger.
  5. Test aim alone, aim with scope/fire held, repeated swipe restarts, and a new action afterward.
  6. Save an exported profile with a clear device/HUD label and record what was actually tested.

A mode change, custom HUD, expanded menu or different weapon can invalidate a positional assumption. Start each probe with a screenshot; during investigation an already-open menu changed the meaning of otherwise correct coordinates.

Playing and calibrating PhoneControl

Connection

Connect your phone with a data-capable USB cable, keep it unlocked and authorize USB debugging. ADB must list it as device, not unauthorized or offline. A visible Samsung USB interface alone did not establish an ADB connection during setup. The successful sequence involved unlocking, toggling USB debugging, reconnecting and accepting the phone's prompt. Do not assume USB-C connectivity means debugging access is available.

Launch the portable app or desktop shortcut, select the phone and click Connect. Click the phone view to give it keyboard focus. The dashboard and video window are separate. Game input is scoped to the foreground phone view, so focusing the dashboard stops held gestures.

Mouse action bindings apply while aiming. In normal mode, right-click means Back rather than scope. Keyboard bindings can operate while the phone view is focused outside aiming. Edit and pause modes suppress gameplay gestures.

Button timing

Hold means a touch remains DOWN while its PC input is held. Tap means one DOWN and an UP about 40 ms later. A press and release occurring between two 8 ms ticks is retained through Raw Input edges; even a very short Hold press receives a short touch instead of disappearing. This is button translation, not an automatic repeated-fire macro.

The starter and saved scope modes differ; see the atlas. A profile Mode controls injected duration, while the game's own scope settings control what the view does with that duration. Verify their interaction in the actual game before changing it.

Aiming continuously

Raw mouse movement supplies signed deltas independent of held mouse buttons. Mouse sensitivity scales them before conversion to a camera swipe. The OS cursor is recentered and confined, but its position is not used as the aiming-motion source. This matters for large sweeps and simultaneous fire/scope.

The camera has a separate logical finger. When its current swipe reaches the allowed envelope, the controller lifts that finger and starts another swipe at the look anchor. Held fire, scope and movement fingers remain down. The Android server must give the new camera gesture an available local ID in 0–9; merely restarting its coordinates is insufficient.

Sprint and autorun

Hold Shift with forward movement to drag the existing movement finger farther upward. Release Shift to return that finger to the walking radius; release movement to lift it. Shift alone does not start running. Forward diagonals use the extended reach. Backward and sideways movement retain normal reach.

Use = to tap the separate autorun/sprint-lock control. It was observed toggling the HUD indicator on and off. Do not map Shift to that button: it creates the persistent autorun behavior that prompted the user's correction.

The Controls page exposes normal joystick radius, sprint reach, sprint key, look anchor and mouse sensitivity. The user later increased saved sprint reach to 30%, while the original successful live probe used 18%.

Supported mappings and practical limits

Supported keys are A–Z, 0–9, =/Equals, Space, Shift, Ctrl, RightAlt, Tab, Enter, Backspace, arrows, F1–F7, F10, F12, five mouse buttons and MouseWheelUp/MouseWheelDown. Choose inputs from the Controls dropdowns; movement and sprint use one input each, while an action dropdown allows multiple selections. For example, select A, MouseWheelUp and MouseWheelDown on Swap weapon to retain the keyboard shortcut and use both wheel directions. Profile JSON stores multiple action inputs as comma-separated names in the existing Key field. Duplicate movement/action/sprint bindings are rejected, including duplicates among an action's selected inputs. Up to 64 actions can be described in a profile, but only ten fingers may be active at once. Already-held input is suppressed when acquiring focus so switching back does not unexpectedly trigger it.

Implemented: wheel actions apply while the phone view is focused and mouse capture is enabled. Each full notch produces a 40 ms tap, even for a Hold action; partial high-resolution deltas accumulate until a notch is complete. Rapid notches queue separately with a released tick between taps. Focus loss, pause, edit, capture and layout changes clear pending wheel input. For Hold actions with several keys selected, releasing one key keeps the action finger down until all selected keys are released. A wheel notch on an already-held action leaves that finger held. These behaviors have local transport regression coverage; physical wheel acceptance in the tested game remains to be confirmed by the player.

Saved settings are at %LOCALAPPDATA%\PhoneControl\settings.json; diagnostics are at %LOCALAPPDATA%\PhoneControl\phonecontrol.log. Exporting a profile makes a reusable layout. App logs rotate around 4 MB. Touch tracing is optional and records DOWN/UP identities and coordinates, rather than every mouse MOVE.

If touches fail, check focus, capture mode, pause/edit state, contextual HUD changes, ammunition and idle protection before changing the transport. The troubleshooting table in Lessons learned gives the order of investigation.

Technical control reference

Components and data path

PhoneControl uses WinUI 3 / .NET 10 for settings and native Win32 input/overlay APIs for gameplay. Official scrcpy 4.1 renders H.264 video/audio in a separate GPU-backed window. A separate Android control-only server is built from scrcpy 4.1 with a modified pointer allocator. The video/audio client and server remain unmodified.

The control path is: Windows Raw Input and key state → InputEngine's 8 ms tick → independent logical fingers → 32-byte touch packets on one persistent TCP stream → loopback ADB forward over USB → Android server → MotionEvent injection → foreground Android application.

The application consumes phone input, lifecycle, capture and discovery ports. AndroidPhoneBackend and DeviceSession implement the current ADB/scrcpy adapter; vendor driver repair is registered separately. See phone backend architecture for contracts and extension guidance. Display geometry comes from the selected phone's effective wm size; invalid dimensions abort connection instead of using a handset-specific fallback.

No per-key adb shell input process is used for gameplay. ADB shell commands are useful for setup/probes but are not the low-latency multitouch transport. The control socket uses NoDelay and a 250 ms send timeout. Serialized writes share a lock; there is no parallel touch writer reordering packets.

Starting the control session

DeviceSession.Connect requires scrcpy version exactly 4.1. It obtains display size using wm size, generates a unique session ID, pushes assets/phonecontrol-control.jar under an app-owned name in /data/local/tmp, and creates a tcp:0 ADB forward to localabstract:scrcpy_<hex-session-id>.

Conceptual command shape, using the actual selected device and session values:

adb -s <serial> push <control-jar> /data/local/tmp/phonecontrol-<scid>.jar
adb -s <serial> forward tcp:0 localabstract:scrcpy_<scid>
adb -s <serial> shell CLASSPATH=<remote-jar> app_process / com.genymobile.scrcpy.Server 4.1
  scid=<scid> video=false audio=false control=true tunnel_forward=true
  send_device_meta=false send_dummy_byte=true clipboard_autosync=false
  power_on=false cleanup=false

These are command shapes; the multiline server example is not a ready-to-paste shell invocation. Consult DeviceSession.cs for the actual ArgumentList construction and 0x formatting. The PC connects to the allocated loopback port and consumes the initial zero dummy byte. It drains the server's outgoing control messages asynchronously.

The renderer is a different scrcpy session with --no-control --video-codec=h264 --max-fps=120 --max-size=1920 --video-bit-rate=16M --video-buffer=0 --print-fps --shortcut-mod=rsuper. Audio uses --audio-buffer=30 or is disabled. The cap/size/bitrate are settings, not immutable constants.

Packet starts with a zeroed buffer, so both button fields remain zero. Mouse-like pressure/flags should not be substituted for finger fields. Width/height are checked as UInt16. Unknown MOVE/UP logical IDs are suppressed, and a new DOWN is rejected if ten fingers are already active.

Android Back is a different 14-byte key-message sequence: type 0, keycode 4, DOWN then UP, with repeat/metastate zero. It is used by normal right-click, not by aiming right-click.

Three different pointer numbers

Logical PC pointer ID: stable ownership across gesture renewal. Joystick = 0; camera = 1; direct cursor touch = 2; action binding index i = 10+i. A logical action ID of 10 or 11 is valid.

Android local pointer ID: allocated by PointersState when a logical gesture goes DOWN. It must stay stable until that gesture goes UP. The custom allocator rotates the next available ID through 0–9 and skips every still-held local ID. A renewed camera gesture keeps logical ID 1 but usually receives a different Android local ID.

MotionEvent pointer index: array position among currently active pointers. Pointer arrays can compact after an UP. Index is not the Android ID or PC logical ID. Do not fix this bug by permanently forcing camera to array index 0; that experiment did not solve swipe renewal.

Android can represent local IDs above 9, but live tests on this handset ignored camera ID 10 and a later action ID 13 while ID 9 still worked. An initial rotation through 0–31 caused periodic input loss until allocation returned to usable slots. The fix limits all local touch IDs to 0–9. This is a measured compatibility behavior; the engine's internal implementation was not inspected.

Camera renewal algorithm

Begin places camera logical ID 1 at (LookX,LookY). For a mouse delta (dx,dy) and displayed viewport (width,height), normalized movement is (dx * sensitivity / width, dy * sensitivity / height).

Large deltas are split into ceil(max(abs(sx)/0.05, abs(sy)/0.08)) steps. Before each step, a target more than 0.17 horizontally or 0.25 vertically from the anchor, or outside 0.01–0.99, triggers camera UP at its previous position and DOWN at the anchor. The current step is then consumed as MOVE, with final coordinates clamped to 0–1. Other fingers are not lifted.

The look finger is established before new action fingers in an aiming tick. Rotating local IDs solved the observed renewal problem; the exact role of game frame batching is not proven. With all ten slots occupied, a freed slot may be the only available replacement, so do not promise a distinct replacement under every possible ten-finger state.

Windows motion, edges and cursor

RawInputReader subclasses the WinUI window and registers keyboard/mouse devices with INPUTSINK. InputEngine explicitly gates events to the foreground mirror HWND. Relative motion accumulates signed deltas; absolute raw samples are converted from 0–65535 to desktop pixels and the first sample only establishes a baseline. The accumulator drains once each tick and resets on mode/focus changes.

Raw key/button edges are combined with asynchronous key-state polling. Duplicate observations are filtered over 32 ms. Short movement presses receive a 40 ms representation. Left/Right Alt are differentiated using the raw keyboard E0 flag; Shift/Ctrl variants are normalized.

The aiming overlay is an almost-transparent native layered, no-activate window. Uniform alpha 1 allows it to own mouse hit tests and hide the cursor via WM_SETCURSOR / SetCursor(0), while keyboard focus stays with the mirror. Color-key transparency is used for the edit overlay instead. Esc, leaving aim, switching to the dashboard and disposal restore the arrow and release ClipCursor confinement.

Cleanup and geometry

Each active logical finger is stored with its latest coordinate. ReleaseAll sends UP for each and clears state. Focus loss, pause, editing, profile changes outside edit mode, geometry changes and normal disconnection release or reset the appropriate gesture state. Cleanup also clears mouse deltas and pending taps so stale motion does not enter a new aim session.

Normal Disconnect closes the TCP client, stops the app's mirror and control processes, removes its own allocated ADB forward and remote JAR. A probe must follow the same ownership discipline; never remove all forwards or terminate every ADB session as routine test cleanup.

Performance interpretation

An 8 ms gesture tick is a target cadence of 125 Hz, not a measured end-to-end latency or game polling rate. Zero added video buffering still leaves capture, encoding, USB, decode, display and game latency. FPS comes from delivered mirror frames. Both frame-rate and touch response should be observed; healthy video does not prove the game accepted an input.

Driving mode and native callback update - 11 October 2026

In 1.0.3, DrivingModeMonitor polls at a 50 ms target cadence on a background task. MirrorFrameCapture reads the foreground mirror's letterboxed video rectangle using a reusable top-down 32-bit GDI DIB. It includes the almost-transparent aiming overlay and discards captures across focus/geometry changes; minimized, portrait, undersized or off-screen views use the phone fallback. It flushes GDI before copying BGRA bytes and restores/deletes its native objects on resize and shutdown. This follows Microsoft's screen capture and DIB synchronization requirements.

Bounded, serialized ADB PNG captures remain a slower background fallback, with one second between completed requests. They run independently so an in-flight screenshot cannot stall fast mirror polling; a healthy current mirror frame takes precedence over a completed fallback. Shutdown cancels/drains the fallback before device cleanup. DrivingHudDetector compares four normalized 24 x 24 arrow regions by luminance correlation (threshold 0.72, at least three matches). Entry uses the first positive observation; exit requires two negatives. The original 1.0.1 two-frame entry and 1.5-second capture delay are superseded. Capture/decode errors preserve the mode. Portrait, blank and nonvehicle images do not match. This reads no game memory and does no capture work in the 8 ms input tick. Poll cadence is not a measured end-to-end latency.

Driving uses Profile.Driving.Bindings with independent logical action fingers 10+i; no walking joystick is injected. Camera remains logical finger 1 with its existing renewal protocol. Transitions release all fingers and suppress held keys before adopting the next layout. Android allocation and the committed control JAR are unchanged. See controls.md and hud.md for evidence and limitations.

The overlay roots its managed owner for the complete native registration lifetime and unregisters its unique class after destruction. This prevents callbacks into a collected delegate, including after reconnect. The regression exercises forced GC, native painting and disposal in a published executable without a phone.

Wheel input and selected action keys - 11 October 2026

Implemented: Raw Input's vertical RI_MOUSE_WHEEL flag reads signed usButtonData separately from button edges and camera deltas. Wheel pulse identifiers are 0x100/0x101, outside the Windows virtual-key range, and are never passed to asynchronous key-state polling. MouseWheelInput accumulates signed deltas in 120-unit notches and preserves every full notch rather than using the button edge sets or 32 ms key deduplication.

Action Key strings may contain comma-separated inputs. Walking/driving validation rejects repeated inputs across or within actions. Multiple held inputs share the same logical action finger 10+i. Wheel taps use that same action's edited position and finger, run through the existing tap lifetime, and wait a released tick before the next notch. They do not renew or release camera/fire/scope fingers. Reset clears queued notches and fractional deltas. The Android protocol, allocator and committed JAR are unchanged.

Phone backends and ports

Current support

Implemented: the Android adapter discovers ADB devices without a manufacturer or model allowlist and obtains the effective display dimensions from Android. Dependency direction

The dashboard is the application's entry adapter. It receives backend registrations containing factories, capabilities, address validation, setup instructions and vendor-driver adapters. App.OnLaunched in Program.cs is the composition root: it registers AndroidPhoneBackend with SamsungDriver, and IosPhoneBackend without Android driver repair. The user selects the backend at runtime; changing it preserves profile/settings data. Adding another vendor driver does not change dashboard discovery or gameplay gestures.

InputEngine depends on IPhoneInput; AimGesture depends on the narrower ITouchSink. DrivingModeMonitor receives independent IMirrorSurface and IPhoneFrameSource ports. Their concrete implementations can be replaced without importing ADB or scrcpy into application input logic. The Windows focus, overlay and raw-input code remains Windows-specific.

Adding an adapter

  1. For another Android vendor with the same transport, use AndroidPhoneBackend. If driver repair is needed, implement IUsbDriverSupport for that vendor and register it in the composition root. Match only that vendor's missing devices and retain download integrity/elevation checks. The shipped repair adapter remains Samsung-only; other vendors currently use their manufacturer's driver installation.
  2. For another transport/platform, implement IPhoneBackend and IPhoneSession and register its factory in the composition root. Supply authorized/ready status and transport explicitly; do not infer automatic connection from an opaque device ID in the dashboard. Backend selection is built in; runtime plugin loading is not. Provide RealtimeInput only when the adapter can maintain independent fingers. Completed-gesture backends need their own interaction view and may implement IPhoneGestureInput; they do not implement fake continuous touch or Android Back methods.
  3. Preserve logical touch ownership independently of backend pointer allocation. Touch coordinates are normalized to the visible phone image; release held touches before changing geometry and notify subscribers afterward. Expose Back as navigation, translate it inside the adapter, and retain a Windows mirror window for focus and overlays.
  4. Bound PNG capture, honor cancellation and drain its worker before removing device resources. Disconnect releases touches and cleans up only this session's resources; the dashboard awaits it before disposal, including connection failure.
  5. Run the self-test and relevant backend tests, then validate a calibrated HUD on the actual phone separately. An interface alone cannot supply an operating system's missing remote-input permissions or transport.

Experimental iPhone connection

What is implemented

PhoneControl can connect to an already running, dedicated WebDriverAgent (WDA) server for an iPhone or an iOS Simulator hosted on a Mac. Select iPhone · WebDriverAgent (experimental) on Connection, enter the server address, choose Use address, then connect to the discovered endpoint.

The separate Windows viewer displays sequential PNG screenshots. Click to tap, drag to send a straight swipe, hold and release for a long press of up to two seconds, or use Home. A gesture is sent after mouse release, as a complete action ending with finger UP. Clicking outside the letterboxed phone image, losing focus/capture, or changing orientation during a pending gesture cancels that gesture locally. One gesture runs at a time. Pointer IDs are not translated into Android pointer IDs.

Screenshot refresh is capped at eight completed captures per second and depends on the server/device. This is an experimental screenshot viewer, not the Android H.264 video/audio stream. Android resolution/bitrate/audio preferences are preserved and apply when selecting Android again. Saved profiles are not replaced by changing the backend.

Not implemented: continuous keyboard/mouse gameplay mapping, held joystick/fire/scope fingers, Android Back, audio streaming, automatic Apple device discovery, or installation/startup of WDA. The adapter exposes no RealtimeInput port and advertises SupportsRealtimeTouch=false; the input engine requires a continuous-input port. iPhone control uses IPhoneGestureInput for completed gestures. Home is an iOS button command, not an Android Back substitute.

Preparing a server

  1. Prepare an iPhone or iOS Simulator with compatible Apple developer tooling and start WDA following the Appium WDA setup guide. Apple development prerequisites are external to the Windows app; no WDA runner or Apple credentials are bundled. Ordinary USB connection alone does not provide these control APIs.
  2. Expose the dedicated WDA REST endpoint to the Windows PC. For example, an externally managed USB forward can expose http://127.0.0.1:8100/; a Mac-hosted simulator requires a reachable Mac endpoint or tunnel. Enter WDA's address, not an Appium server address.
  3. Use an instance with no existing WDA session. WDA's create-session route replaces its previous session, so PhoneControl checks reported session ownership and refuses to take over an active session. Keep the instance exclusive while connecting. This preflight is not an atomic lock against another client.
  4. Connect manually. The endpoint is always classified as Network, including a loopback USB forward or remotely hosted simulator. It does not trigger the one-USB-phone auto-connect rule or Samsung driver repair.
  5. Disconnect before changing the backend or address. PhoneControl cancels/drains its captures and commands, closes its viewer and deletes only the WDA session ID it created. It leaves the external runner, device applications, tunnels and other sessions alone. If a create-session response is lost after WDA accepted it, ownership cannot be proven; close that abandoned session externally before retrying.

Addresses must use HTTP(S), without embedded credentials, query parameters or fragments. The address preference stays in the app's local settings. Keep the unauthenticated WDA service on a trusted private connection; the app does not expose or install that service.

Geometry and bounded operations

The owned WDA session explicitly sets screenshotQuality=0 before capture, so the client receives PNG rather than relying on a JPEG/HEIC server default. Wire payloads use explicit JSON keys and are tested after obfuscation.

WDA's /window/size reports gesture viewport points; PNG dimensions report screenshot pixels. The adapter maintains them separately. It checks geometry before and after a capture, validates image dimensions/size and discards captures crossing an orientation change. Commands check current viewport geometry before submission. The viewer maps clicks relative to the displayed image, with no touches in letterboxing.

Each HTTP operation has a five-second timeout; screenshots and JSON responses have size limits. Captures are serialized with control commands. The UI retains at most the current decode and newest pending image. The implementation submits finite gestures with UP in the same request; cancelling a request is not proof that XCTest interrupted a gesture already executing on the phone. There are no persistent held fingers to release through the Android protocol.

The touch-ID mistake in detail

The first custom allocator used Android's wider 0–31 ID space. It fixed immediate camera restart failure in short tests, which made it look successful. Longer user testing exposed that aiming and newly pressed buttons stopped together and recovered later.

A fresh control-server probe held scope and advanced camera gestures through local IDs. The scoped scene moved at ID 9; the same gesture did not move the scene at ID 10. A new action with ID 13 did not open the backpack. This directly supported a compatibility boundary rather than an assumed USB backlog.

The corrected allocator rotates only available slots 0–9. A live test kept scope down through 128 camera restarts, verified rotation at the final restart, then opened the backpack immediately with a fresh action. The user tested the installed build and replied “it worked!” The allocator regression test now asserts the local-ID range for renewed cameras and actions, not just uniqueness.

The observed cutoff does not prove the game's internal data structure. Record the behavior and the tested workaround without presenting an uninspected engine implementation as fact.

General rules for future changes

  • Success at the operating-system API is not proof of acceptance by the game. Android-valid IDs still failed at the application level.
  • Preserve identity for every held gesture, but allocate a fresh compatible identity for a restarted gesture when available.
  • Keep logical identity, Android local identity and array index separate in code, logging and tests.
  • Test beyond one full allocation cycle. The regression performs 128 renewals and creates a new action on every iteration.
  • Test an action first pressed after the stress case. Already-held fingers can remain usable while new fingers fail.
  • Recenter the cursor for usability; obtain aim movement from Raw Input rather than cursor-position differences.
  • Separate a toggle control from an analog gesture. “Sprint” and “autorun” were visually/functionally distinct despite similar running results.
  • Preserve edited profiles during upgrades. A source starter is not the user's saved truth.
  • Verify the correct screen and awake state before a probe, and its expected result afterward. The initial corrected-server probe began in a menu; it was repeated in actual gameplay before claiming the scoped test passed.
  • Keep video and control experiments isolated. A temporary server and forward should not interrupt the app's renderer or another device session.
  • Do not turn an unverified theory into extra infrastructure. Transport flooding was considered, but the local-ID cutoff provided direct evidence and a narrower fix.
  • Record delivered FPS and clearly label latency as unmeasured. The 120 FPS cap did not make the observed 60 FPS game run faster.

Troubleshooting order

  1. Capture a fresh phone frame. Check idle protection, the expected gameplay screen, weapon, menu state, ammo and contextual prompts.
  2. Confirm the mirror is foreground, aiming is enabled for mouse actions, and pause/edit modes are off.
  3. Inspect the saved profile and coordinate convention. Check for a user-edited key, mode or reach rather than assuming defaults.
  4. Check DOWN/UP tracing, geometry and the logical finger that owns the gesture.
  5. For restart failures, instrument Android local IDs and test repeated renewals plus a new action; compare 0–9 with the failing build only in an isolated probe.
  6. Inspect stream/control disconnect errors and USB authorization if the session itself failed.
  7. Apply a narrow correction, run relevant allocator/transport checks, republish the complete folder, reconnect and verify actual gameplay.

Tempting fixes that were insufficient

Moving the camera to the first MotionEvent array index did not solve renewal. Merely resetting the camera coordinates without changing local identity was insufficient with a held action. Rotating through every Android-valid ID passed short tests but broke long tests. Repeated ADB shell swipes would discard the persistent multitouch model rather than repair it.

A physical mouse check remains valuable after transport tests: it covers focus, capture, raw input, overlay and the player's actual gesture timing together. This is how the final fix was accepted.

Installed dashboard crash - 11 October 2026

Observed: Windows Application/.NET event 1025 records A callback was made on a garbage collected delegate for MappingOverlay+WndProc, followed by FailFast/coreclr exception 0x80131623. This signature was recorded on 3 and 11 October. The dashboard/input process dies while the independent scrcpy renderer survives, explaining video without keybinds.

Implemented remedy: USER32 holds a function pointer, not a managed GC root. Each overlay explicitly roots its owner while the native window/class exist, registers a unique class per instance, destroys the window and unregisters its class before releasing the root. Reusing a fixed class name retained the first instance's callback across reconnects; merely keeping the new instance's delegate field was insufficient. Disposal is idempotent; failed native cleanup retains the root to avoid dangling pointers. Raw Input initialization removes its subclass if device registration fails.

The published regression creates 12 overlays through weak references, forces full GC before native painting, disposes each twice and verifies collection afterward. This covers callback lifetime, class reuse and root cleanup. Long physical gameplay remains a separate acceptance check; ordinary exception logging cannot repair this FailFast.

Safe live regression sequence

  1. Confirm an awake, normal gameplay HUD and expected saved profile. Capture the initial frame. Release active touches before starting an isolated probe.
  2. Verify a simple known action, such as opening/closing Backpack. Avoid spending currency or altering inventory.
  3. Compare walking, forward sprint and returning to walking on the same joystick finger. Observe stamina rather than relying on a similar animation.
  4. Capture aiming with no button, with scope held, and with a brief fire press. Avoid prolonged firing that consumes the account's ammunition.
  5. Exercise long horizontal/vertical sweeps, both directions, through more than one full local-ID cycle. Keep another action finger held.
  6. After the sweep, press an action that was not previously held, then movement/jump. Check immediate response, not delayed recovery.
  7. Release capture with Esc, switch windows, pause, edit and disconnect; check that no movement/fire/clip remains stuck.
  8. Reconnect using the published JAR and perform a physical 30-second mouse test. Record the result separately from direct injected touch probes.

Implemented: development uses feature/* branches and pull requests into main. A release is stabilized on release/<major.minor.patch>, with fixes committed there and merged back into main. This installer targets Intel/AMD x64 Windows 11, build 26100 (24H2) or newer. Release testing covered this Windows 11 x64 development PC, not every supported OS build. Device onboarding and driver repair

The app polls bundled ADB every two seconds while disconnected, with guards against overlapping discovery/connection/driver operations. An unauthorized phone receives a handset-consent instruction; an offline phone receives a reconnect instruction. When exactly one ready device is present on the Connection page, automatic connection starts once. A serial containing : is excluded from automatic connection because it usually denotes a network/emulator endpoint. Multiple devices require choosing a phone; this avoids connecting an arbitrary emulator when several are running.

Automatic connection is enabled by default and can be disabled with its Connection-page toggle. An explicit disconnect suppresses automatic connection for the rest of that app session. A failed automatic connection is not retried continuously; use Refresh devices / Connect or unplug/replug. Returning to Connection permits discovery-driven connection. Saved profiles are loaded before connection and are not replaced by the starter layout. A per-user/session mutex prevents two new PhoneControl copies from running their input controllers simultaneously; opening a second copy brings the existing dashboard forward.

SamsungDriver.HasMissingDriver() reads present Windows device nodes using Configuration Manager APIs. Only a Samsung USB hardware ID (USB\VID_04E8&…) reporting problem code 28, missing driver, and no ADB devices, triggers automatic repair. It is attempted once per app run. An already functioning driver is not replaced automatically. An unrecognized manufacturer, disabled debugging or an unplugged phone does not silently trigger Samsung installation. The user can also request Repair Samsung USB driver while disconnected.

Repair downloads the original Samsung USB Driver for Mobile Phones 1.9.5.0 from Samsung's official site into a unique user-local staging directory. The release's SHA-256 pin is:

0ECC9E47D836A7CFF7215EC9CDF33DC7F3E416A7D5EDEDAD522B978B2EB84A20

The download is limited to 60 MB and three minutes. A mismatched download is deleted and never executed. The reviewed pinned binary has an NSIS-3 outer installer; repair passes NSIS's case-sensitive /S switch and requests elevation for that vendor installer alone. PhoneControl stays unelevated. Exit code 3010 asks for a convenient user restart; no forced restart is issued by PhoneControl. Other errors and declined elevation are shown with a retry option. Cancellation closes an incomplete download; closing PhoneControl does not terminate an already-started elevated driver installation.

Not yet verified: the complete Samsung silent-driver flow on a clean Windows PC, including vendor child-process behavior, restart behavior and whether any vendor screens remain. The existing working driver was preserved during development. /S is supported by NSIS, but that fact alone does not prove every vendor-specific step is unattended. Do not advertise the driver path as zero-touch until clean-PC acceptance passes. Proprietary Samsung binaries are downloaded at runtime rather than committed or redistributed inside our installer.
